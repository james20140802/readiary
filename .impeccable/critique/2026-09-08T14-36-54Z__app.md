# Readiary 제품·UI 검토 — 2026-09-08

검토 기준: main `73cf0db`, 노션 Readiary 개편 계획·결정 로그, `docs/ui-guidelines.md`, 실제 구현. Frontend Design Premium(및 frontend-design), Build Web Apps, Impeccable critique를 적용했다. 독립 디자인 평가와 자동 검사·브라우저 증거를 별도로 수집한 뒤 합쳤다.

범위: 공개 랜딩·로그인·회원가입은 프로덕션 화면과 코드, 로그인 이후 오늘·책장·프로필·소셜·알림은 코드로 검토했다. 보호된 페이지는 로그인 화면으로 리다이렉트되어 실제 데이터로 동작을 재현하지 않았다. 공개 화면의 다크모드 데스크톱, 랜딩·로그인의 390×844 화면을 확인했다. 라이트모드는 CSS 색상 계산으로 확인했으며 실화면·iPhone·VoiceOver 검증은 하지 않았다. 계정 생성·기록 저장·알림 발송은 실행하지 않았다. 랜딩의 남기기 데모만 작동시켰다.

## 제품과 디자인 판단

Readiary는 문장과 생각을 부담 없이 남기고 시간이 흐른 뒤 다시 읽는 독서 일기다. 입력 비용을 낮추고, 배지 대신 회고를 보상으로 삼는다. 마루 부리의 문장, Pretendard의 도구, 따뜻한 종이와 파란 잉크는 이 목적과 잘 맞는다. 책등·원고·발췌집·엽서·프로필 책은 일반 서비스와 구별되는 특징이다.

가장 큰 개선 기회는 장식을 더하는 것이 아니라 **기록 → 책 선택 → 회고 → 원문 다시 읽기**가 끊기지 않게 만드는 것이다. 은유는 유지하되 사용자가 예상하는 다음 행동을 실제로 제공해야 한다.

좋은 점:

- 첫 화면의 “하루 한 문장이면 충분한 독서 기록”은 제품의 가치와 행동을 함께 설명한다. 모바일에서도 제목·설명·주요 버튼의 위계가 분명하다.
- 최근 책 기본 선택과 저장 후 선택적 덧붙이기는 기록 부담을 낮춘다.
- 책장은 표현력 있는 책등과 실용적인 목록을 함께 제공한다. 프로필·엽서에는 제스처 외의 명시적인 버튼도 있다.
- 알림 설정은 빈도·기기 범위·사용 불가 이유를 설명한다. 인증 폼은 이름 있는 필드와 자동완성 속성을 갖춘다.

## 우선 개선할 사항

### P1 — 문장을 쓰다가 다른 책을 고르면 입력을 잃을 수 있다

- 근거: `app/protected/dashboard/_components/Composer.tsx:39`의 입력은 컴포넌트 state에 있고, `:268`의 “내 책”은 책장 페이지로 이동한다. 현재 입력을 전달하거나 복구하는 경로가 없다. 코드 확인이며 운영에서 기록을 작성해 재현하지 않았다.
- 사용자 영향: 문장부터 적은 뒤 목록에 없는 책을 선택하려는 순간 기록 흐름이 끊긴다.
- 제안: 같은 화면의 검색·선택 UI에서 책을 바꾸고 입력을 유지한다. 화면 이탈·세션 만료의 초안 복구 범위는 별도로 정한다.
- 완료 기준: 모바일에서 문장을 입력하고 목록 밖 책을 선택한 뒤 동일한 문장을 저장할 수 있다. `$impeccable harden`/`shape` 대상.

### P1 — 옅은 글자색이 실제 라벨·조작 문구에도 쓰인다

- 근거: `app/globals.css:21`, `components/ui/FormLabel.tsx:15`, `components/books/BookList.tsx:68`. 라이트 `#A39A8D`와 종이 `#F7F3EC`의 대비는 **2.51:1**, 카드 `#FDFBF7`에서는 **2.69:1**이다. 장식만이 아니라 작은 라벨·비활성 선택지·저자·기록 링크에도 쓰인다.
- 다크는 별도로 판단해야 한다. 같은 토큰의 실제 다크 값 `#8E8476`은 종이 위 약 4.88:1, 카드 위 약 4.48:1이다. CSS 주석의 “4.5:1”을 그대로 통과 근거로 삼을 수 없다.
- 제안: 읽고 조작해야 하는 텍스트와 장식용 옅은 먹을 구분한다. 필수 라벨·보조 정보·조작 문구는 충분한 대비의 의미 토큰을 사용한다.
- 완료 기준: 작은 일반 텍스트는 실제 표면별 4.5:1 이상을 확인한다. 색감을 유지하면서 라이트·다크에서 검증한다. `$impeccable audit`/`typeset` 대상.

### P2 — 월별 회고에서 문장의 나머지를 읽을 수 없다

- 근거: `components/profile/ProfileBook.tsx:376` 이하의 월별 인용은 `line-clamp-3`인 일반 문단이다. 원문 링크·펼치기·월별 전체 보기 동작이 없다.
- 사용자 영향: 다시 읽고 싶어진 문장을 찾으러 다른 화면을 직접 탐색해야 한다.
- 제안: 인용에서 기록 상세로 이동하거나 “이 달의 기록 보기”를 제공한다. 필요한 ID를 bounded preview에 포함하는 방향으로 설계한다.
- 완료 기준: 긴 문장을 클릭·키보드로 끝까지 읽고 원래 회고 위치로 돌아온다. `$impeccable shape` 대상.

### P2 — 랜딩 체험 안내와 실제 행동이 다르다

- 근거: `components/landing/LandingShelf.tsx:19`는 책등을 누르면 표지가 펼쳐진다고 설명하지만 `components/landing/demo.ts:35` 이후의 책 링크는 `/signup`이다. 프로덕션 접근성 트리에서도 확인했다.
- 추가 근거: `components/landing/LandingComposer.tsx:66`의 “생각 덧붙이기”, “페이지 남기기”는 핸들러 없는 칩이다. 모바일 실화면에서 “남기기” 후 “생각 덧붙이기”를 눌러도 화면이 바뀌지 않았다. 입력처럼 보이는 영역도 실제 편집 필드가 아닌 자동 타이핑 데모다.
- 제안: 안내한 범위의 샘플 체험을 완성하거나, 조작 가능한 것과 미리보기를 구분한다. 클릭 결과가 가입이라면 이를 문구로 예고한다.
- 완료 기준: 모든 활성 데모 컨트롤이 설명한 결과를 제공한다. `$impeccable clarify`/`harden` 대상.

### P2 — 가장 빠른 기록 화면에서 공개 범위가 불명확하다

- 근거: `Composer.tsx:40`은 `isPrivate=false`, `:280` 이하에는 “비공개” 토글만 있다. 전체 기록 폼 `components/entries/EntryFormBody.tsx`에는 친구 열람·별도 링크 공유 설명이 있지만 홈에는 없다.
- 사용자 영향: 사용자는 토글을 끈 상태가 친구 공개인지 인터넷 전체 공개인지 알기 어렵다. 보안 취약점이 확인됐다는 뜻은 아니다.
- 제안: “친구에게 보임 / 나만 보기”처럼 현재 대상이 드러나게 표현하고 외부 링크 공유는 별도임을 짧게 설명한다.
- 완료 기준: 두 공개 상태와 외부 공유 활성화의 차이를 저장 전에 이해할 수 있다. `$impeccable clarify` 대상.

### P2 — 회원가입 안내가 세 체크박스를 ‘두 항목’이라고 부른다

- 근거: `app/signup/page.tsx:223`의 문구와 `components/auth/ConsentFieldset.tsx`의 나이·개인정보·약관 세 필수 체크박스. 공개 화면에서도 세 항목을 확인했다.
- 제안: 실제 필수 확인 항목과 안내를 일치시킨다. “필수 항목을 모두 확인하면…”처럼 개수에 의존하지 않는 문구가 가능하다.
- 완료 기준: 가입 방식과 관계없이 요구 사항과 안내가 일치한다. `$impeccable clarify` 대상.

### P2 — 삭제된 기록의 알림이 아무 동작 없는 버튼으로 남는다

- 근거: `app/protected/social/_components/NotificationList.tsx:139` 이하. 이동할 기록이 없을 때 핸들러 없는 버튼으로 렌더링한다.
- 제안: “삭제된 기록” 상태가 드러나는 비상호작용 항목으로 표시한다.
- 완료 기준: 클릭·키보드 탐색에서 열 수 없는 알림을 행동 가능한 항목으로 오해하지 않는다. `$impeccable harden` 대상.

## 전체 시스템에서 다듬을 부분

- 괘선 입력의 포커스: `components/ui/Input.tsx:40`은 outline을 제거하고 1px 선색만 바꾼다. 다크 강조 경계와 바탕 대비는 약 1.78:1이다. 괘선 문법 안에서 굵기·명도 등으로 포커스를 더 명확히 할 수 있다. 실제 키보드 전체 검증은 남아 있다.
- 터치 여유: 공개 인증 화면의 기본 버튼은 높이 40px, 비밀번호 표시 버튼은 34×34px이었다. 작은 텍스트 링크와 함께 모바일의 44px 권장 터치 영역을 검토한다. 모든 작은 요소를 곧바로 접근성 규정 위반으로 단정하지 않는다.
- 비밀번호 오류: 회원가입의 공통 `passwordError`가 확인 필드에만 연결되어 원래 비밀번호의 길이 오류를 다른 칸의 문제처럼 보이게 할 수 있다. 규칙은 사라지는 placeholder 외에도 유지되는 도움말로 전달할 수 있다.
- 랜딩 구성: 8개의 화면 높이 장면이 분위기를 잘 만들지만, 첫 방문자가 기능을 빠르게 훑기에는 길다. 핵심 체험 접근과 섹션 이동 신호를 개선할 여지가 있다. 이는 사용성 제안이며 이탈률이 측정됐다는 뜻은 아니다.
- 문서: README의 배지·Next.js 14, 가이드의 과거 다크 토큰, 그림자 금지와 입체 표현의 차이를 정리할 필요가 있다. 기존 책·엽서 효과를 단순 위반으로 보고 일괄 제거하지 않는다.

인지 부하는 랜딩 첫 화면에서 낮고, 책 선택과 회고 원문 탐색에서 증가한다. 차분한 첫인상 → 쉬운 한 문장 → 쌓인 책장의 애착은 좋은 감정 흐름이다. 예상한 행동이 이어지지 않는 순간에 신뢰가 떨어질 수 있다.

사용자 관점:

- 이동 중 휴대폰 독자: 문장을 쓰고 책을 바꾸려다 입력을 잃는 상황이 가장 위험하다.
- 첫 방문자: “펼쳐진다”는 안내 후 가입으로 이동하거나 데모 버튼이 멈추면 기능 자체를 오해할 수 있다.
- 키보드·저시력 독자: 희미한 라벨·포커스, 동작 없는 알림이 탐색을 어렵게 만든다.

자동 검사: `detect.mjs --json app components` 결과 **0건**, exit 0. 제품 맥락·동작·대비에 관한 위 수동 발견을 검사 통과가 무효화하지 않는다. 거짓 양성은 없었다.

## 추가 규칙 제안 — AGENTS.md에는 아직 의무화하지 않음

1. **UI 변경 검증:** 모바일 폭·라이트/다크·키보드와 로딩/빈 상태/오류 상태를 해당 범위에 맞게 확인하고 PR에 증거를 남긴다. iOS PWA는 별도로 구분한다.
2. **문서와 구현의 일치:** 시스템 결정 변경 시 관련 가이드·토큰·컴포넌트를 함께 갱신한다. 과거 계획과 현재 상태가 다르면 차이를 명시한다.
3. **완료 단계 구분:** 코드 완료, Draft PR, 최신 head 검사, 리뷰 해결, 머지, 배포, 마이그레이션, 실기기 확인을 각각 보고한다. CI만으로 프로덕션 정상 동작을 단정하지 않는다.
4. **공개 범위 계약:** 개인정보·공유 변경은 UI·API·RLS·Storage·캐시와 운영 문서를 함께 검증한다. 환경 파일·비밀키는 worktree에 임의 복사하거나 커밋하지 않는다.
5. **데이터와 선택 UX:** DB 집계·bounded preview·검색·페이지네이션을 우선하고, 전체 기록 선조회로 목록을 채우지 않는다. 현재 선택을 먼저 보이고 변경·해제·키보드·개별 실패 복구를 제공한다.

판단할 질문: 다른 책을 고르는 일이 작성 화면을 떠날 이유가 있는가? 회고의 목적이 미리보기라면 어디에서 원문을 끝까지 읽는가? 문학적 은유가 다음 행동을 가리는 지점은 어디인가?

권장 순서: 초안 보존과 읽기 대비 → 회고 원문 연결 → 공개 범위 안내·데모 일치 → 문서 및 세부 조작 정리. 이번 작업에서는 UI 코드를 수정하지 않았다.
