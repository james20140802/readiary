# 이메일 소식 수신 동의 운영

## 범위와 상태

서비스 새 기능·리뉴얼·이벤트 이메일만 선택 대상으로 한다. 개인 독서 기록을 활용한 요약, 기존 회원 일괄 발송, 캠페인 작성·예약, 실제 발송은 이 변경에 포함하지 않는다. 인증 메일과 Web Push 동의는 별개다.

신규 독자는 이메일·Google 인증 후 프로필 설정(온보딩)에서 기본 미선택 항목을 선택한다. 온보딩은 체크박스 한 줄과 "보기"만 두고, 목적·항목·보유 기간·거부할 권리 안내(개인정보 보호법 제15조 제2항)는 "보기"로 펼친다(접혀 있어도 `aria-describedby`로 함께 읽힌다). 알림 설정은 설명 전문을 그대로 보인다. 문구 버전 `email-news-v1`은 이 두 표시를 함께 가리키며(수집 경로 `onboarding`/`settings`로 구분), 첫 동의 기록 전(2026-10-27, 기록 0건)에 정했다. 기존 독자는 알림 설정에서 직접 선택한다. 약관 동의 시각과 계정 메타데이터를 홍보 수신 근거로 해석하지 않는다.

## 저장·접근 계약

- `email_preferences`: 현재 동의, 대상 이메일, 버전, 동의·철회 시각. 본인 읽기만 허용한다.
- `email_consent_events`: 목적(`service_news_events`), 채널(`email`), 문구 버전(`email-news-v1`), 서버 처리 시각, 경로와 요청 ID. 프로필 원문을 복제하지 않고 재시도 비교용 해시만 저장한다. 기존 문구 버전의 의미를 바꾸지 않는다.
- `email_deliveries`: 발송 요청 ID, 대상 이메일, 동의 버전, 본문 해시, 수신거부 토큰 해시, 전송 상태. 일반 회원에게 노출하지 않는다.
- 쓰기 RPC는 service_role만 실행한다. API는 최신 사용자 인증 후 본인 ID를 지정하며 브라우저가 제공한 대상 ID·이메일·시각·수집 경로를 신뢰하지 않는다. 화면의 계정 ID가 현재 인증과 다르면 충돌로 반환한다. 새 동의는 화면에 표시한 `expectedEmail`을 함께 보내고, DB의 사용자 행을 잠근 뒤 현재 주소와 일치할 때만 저장한다. 주소가 바뀌면 `409 consent_conflict`로 재확인을 요구한다. 철회는 주소가 달라도 허용한다.
- 변경 요청 ID는 네트워크 오류·응답 유실 재시도에 유지한다. 재전송은 현재 상태를 반환하며 이전 쓰기를 다시 실행하지 않는다. 같은 요청 ID의 표시 주소를 바꾸면 충돌로 반환한다. 비교를 위해 `requested_email`을 이력에 저장한다. 다른 요청은 기대 버전을 검사한다. 가입의 프로필 생성·선택 저장은 하나의 트랜잭션이다.
- 이메일 주소 변경/인증 해제는 DB 트리거로 동의를 철회한다. 주소를 되돌려도 자동 동의하지 않는다.
- `auth.users` 삭제 시 현재 상태·동의 이력·발송 처리 기록은 CASCADE로 삭제한다. 공급자의 이미 전달된 메일·로그·백업은 별도 수명이며, 이를 앱 DB 삭제와 혼동하지 않는다.

## 수신거부와 발송 경계

본문 링크는 `/email/unsubscribe#<token>`이다. 화면 GET은 상태를 변경하지 않는다. 화면은 토큰을 메모리로 옮기고 주소 표시줄에서 제거한 뒤 사용자의 버튼 조작으로 POST한다. 새로고침해 토큰을 잃으면 원래 메일 링크를 다시 연다. 로그인·비용 없이 이용할 수 있다.

메일 클라이언트의 원클릭 수신거부는 `List-Unsubscribe` URL과 `List-Unsubscribe-Post` 헤더를 사용한다. 서명으로 생성된 추측 불가능한 토큰의 해시를 DB와 대조한다. 해당 POST에는 세션이나 Origin을 요구하지 않고, 일반 화면의 JSON POST에는 동일 출처를 요구한다. 이미 철회한 링크도 성공 처리한다. 탈퇴한 계정의 링크는 사용 불가 안내로 응답한다.

토큰은 앱 로그, 분석, PWA 캐시에 기록하지 않는다. 원클릭 헤더 URL에는 토큰 쿼리가 필요하므로 **프록시·호스팅·관측 도구의 요청 URL 수집에서 `/api/email-unsubscribe` 쿼리를 제거하는 설정을 운영 활성화 전에 확인한다.** 코드만으로 외부 접근 로그의 보관을 보장하지 않는다.

`sendMarketingEmail`은 호출 경로/cron 없이 준비된 서버 전용 어댑터다. DB에서 계정 존재·인증 이메일·현재 동의를 확인하고 전송 직전에 다시 동의 버전을 확인한다. 조회 실패는 발송 제외다. 동일 delivery ID의 대상·내용·토큰·동의 버전을 바꿀 수 없다. 병렬 요청에는 2분의 중복 호출 유예가 적용된다.

Resend에 넘긴 뒤에는 철회로 메일을 회수할 수 없다. DB 검사와 외부 HTTP 사이를 하나의 트랜잭션으로 만들 수 없으므로 이 경계를 안내한다. 인증 메일을 막는 전역 suppression을 홍보 철회에 사용하지 않는다. Resend Contacts 일괄 동기화도 하지 않는다.

응답 유실은 `unknown`으로 남기고 같은 ID·내용으로만 23시간 이내 재시도한다. 23시간이 지난 미확정 요청은 자동 재전송하지 않고 Resend 결과를 운영자가 대조한다. 성공 결과 저장 실패도 미확정으로 취급한다. Resend의 24시간 멱등 보관에만 장기 중복 방지를 의존하지 않는다.

## 활성화 순서

1. Draft PR 검토 후 별도 머지 절차를 따른다. 마이그레이션 `20261007090000_email_marketing_consent.sql`을 먼저 적용하고 service_role RPC, 인증 사용자 본인 읽기, 익명/타인/직접 쓰기 차단을 실제 환경에서 확인한다.
2. 이메일 소식 처리 내용은 `/privacy` 본문 조문(제1·2·3·5·6·8조)에 넣어 **2026-10-27 공고, 2026-11-03 시행**으로 확정했다. `/privacy`·`/terms` 위에는 개정 안내와 지난 판(`/privacy/2026-09-15`, `/terms/2026-09-13`) 링크를, 오늘 화면에는 시행일까지 닫을 수 있는 한 줄 안내(`PolicyNotice`)를 둔다(`lib/legal/texts.ts`의 `LEGAL_ANNOUNCED`·`PRIVACY_EFFECTIVE`, 방침 제11조의 7일 고지). 공고일에 프로덕션에 배포돼 화면에 실려야 공고한 것이다. 배포가 늦어지면 두 날짜를 함께 미룬다. 개인정보 이용·광고 수신 선택 문구, Google 로그인 이메일 선택 이용과 Resend 이전 조건을 함께 확인한다. 공고를 했다고 소급 기록하지 않는다.
3. 승인된 공급 경로로 `SUPABASE_SERVICE_ROLE_KEY`를 서버에 설정한다. 실제 시행일을 ISO 형식 `EMAIL_CONSENT_EFFECTIVE_AT`(`2026-11-03T00:00:00+09:00`)에 지정하고 `EMAIL_CONSENT_ENABLED=true`로 수집을 연다. 날짜 전에는 신규 선택을 받지 않는다. 수집 플래그를 꺼도 저장된 상태 조회·철회는 유지하며 수신거부 API를 차단하지 않는다.
4. 이후 캠페인 작업 시 `RESEND_API_KEY`, `EMAIL_MARKETING_FROM`, `EMAIL_MARKETING_SENDER_INFO`(발신자·연락처), HTTPS `EMAIL_PUBLIC_ORIGIN`, 32자 이상 무작위 `EMAIL_UNSUBSCRIBE_SECRET`을 별도로 공급한다. 기존 Supabase SMTP 자격 증명이 앱 서버에도 있다고 가정하지 않는다. 키를 파일로 복사하거나 로그/PR에 노출하지 않는다.
5. `EMAIL_MARKETING_SEND_ENABLED`는 이번 작업에서 **설정하지 않는다**. 모든 텍스트 메일에 `(광고)`와 발신자 정보, 수신거부 경로를 추가하는 어댑터만 준비한다. 추적 비활성화·공급자 보관 설정과 쿼리 로그 제외를 확인한 후 별도 캠페인 승인으로 활성화한다.

Resend 도메인은 착수 시 읽기 전용 조회로 인증 완료, 도쿄 리전, 열기/클릭 추적 꺼짐을 확인했다. 실제 SMTP 사용과 별개로 이번 코드의 새 API 키 공급 및 실발송은 검증하지 않았다. 토큰 시크릿을 바꿀 때 기존 수신거부 토큰 해시는 유지한다. 이전 미확정 발송을 바뀐 시크릿으로 재시도하지 않는다.

## 현재 운영 상태 (2026-10-29 확인)

- 운영 DB: 마이그레이션 `20261008132320`(저장소 파일명 `20261007090000_email_marketing_consent.sql`) 적용, 동의·철회·권한 검증 완료(PR #131).
- 공고: 2026-10-27 프로덕션 배포(PR #157)로 개정 방침을 공고했고 시행일은 2026-11-03이다.
- 환경변수: 운영자가 2026-10-27에 Vercel Production에 `EMAIL_CONSENT_EFFECTIVE_AT`·`EMAIL_CONSENT_ENABLED`를 등록했다. 등록 뒤 프로덕션 배포는 2026-10-29 PR #158(`a7cc30b`)이다. 값과 `SUPABASE_SERVICE_ROLE_KEY` 존재 여부는 도구 권한상 이 기록에서 직접 확인하지 못했다.
- `emailConsentAvailable()`은 `ENABLED=true`이고 현재 시각이 시행 시각 이후일 때만 참이므로 2026-11-03 00:00(KST) 전에는 새 동의가 열리지 않는다. 시행일 이후 확인 항목은 아래 "시행일 확인"을 따른다.
- `EMAIL_MARKETING_SEND_ENABLED`와 발송용 키는 설정하지 않았다. 동의 수집이 열려도 메일은 나가지 않는다.

## 시행일 확인 (2026-11-03 이후)

1. 운영 환경에서 신규 이메일 가입과 Google 가입 각각 온보딩까지 진행해 이메일 소식 항목이 기본 미선택이고, 선택하지 않아도 가입이 끝나는지 본다.
2. 기존 계정의 알림 설정에서 "준비 중" 안내가 사라지고 선택·저장할 수 있는지 본다. 화면에 Readiary 명칭, 처리 결과, 날짜가 나오는지 본다.
3. 동의 뒤 철회까지 진행하고 `email_preferences`·`email_consent_events`에 본인 행과 경로(`onboarding`/`settings`)가 남는지 DB에서 확인한다. 기존 회원의 행이 새로 생기지 않았는지(소급 동의 없음)도 확인한다.
4. 두 탭으로 오래된 화면 저장 시 `409`와 재확인 안내가 나오는지 본다.
5. 모바일 폭·라이트/다크·키보드로 위 화면을 확인한다. iOS 설치 PWA와 실기기는 결과를 따로 적고, 못 했으면 미검증으로 남긴다.

## 수집 중지와 재개

동의 문구나 처리 조건에 문제가 생기면 새 수집만 멈춘다. 이미 받은 동의와 철회 경로는 그대로 둔다.

1. Vercel Production 환경변수 `EMAIL_CONSENT_ENABLED`를 `false`로 바꾼다(삭제해도 같다). 서버 함수가 런타임에 읽는 값이지만 새 값은 이후 배포부터 확실히 반영되므로, 바꾼 뒤 현재 프로덕션을 다시 배포(Redeploy)한다.
2. 확인: 알림 설정에 "새 신청은 준비 중이며 수신거부는 계속 가능합니다."가 보이고 동의 저장 버튼이 막힌다. 기존 동의자는 철회를 저장할 수 있다. 온보딩에서 동의를 보내면 API가 `503`으로 거절하고, 동의 없이는 가입이 끝난다. `/email/unsubscribe`와 `/api/email-unsubscribe`는 플래그와 무관하게 동작한다.
3. 이미 저장된 동의를 운영자가 일괄 철회하거나 지우지 않는다. 문구 자체가 잘못돼 기존 동의를 쓸 수 없다고 판단하면, 발송을 하지 않는 상태로 두고 새 문구 버전(`email-news-v2`)으로 다시 받는 작업을 별도로 연다.
4. 중지 사유·일시·재개 조건을 노션 이슈와 이 문서에 기록한다.
5. 재개는 `EMAIL_CONSENT_ENABLED=true`로 되돌리고 다시 배포한 뒤 위 "시행일 확인" 1·2를 반복한다. 문구나 처리 조건을 바꿨다면 방침 개정 공고(7일)를 먼저 거친다.

## 운영 담당자와 정기 확인

- 담당자: Readiary 운영자(개인 개발자, 개인정보처리방침 제10조의 개인정보 보호책임자)가 동의 수집·중지·철회 문의·정기 확인을 맡는다. 연락처는 방침 본문을 따르고 이 문서에 따로 적지 않는다.
- 처리 결과 알림: 정보통신망법 제50조 제7항에 따라 동의·철회 처리 결과(전송자 명칭, 일시, 처리 결과)를 알린다. 현재는 알림 설정·수신거부 화면에 즉시 표시하는 방식이며, 별도 알림 메일은 보내지 않는다.
- 2년 주기 확인: 같은 법 시행령 제62조의3에 따라 동의일부터 2년마다 수신 동의 여부를 확인해 알려야 한다. 첫 동의가 2026-11-03 이후이므로 가장 이른 확인 기한은 2028-11-03이다. 확인 안내(전송자 명칭, 동의 일시·내용, 유지·철회 방법)는 발송 기능과 함께 만들고, 그 전까지 이 기한을 노션 이슈로 남겨 둔다.
- 광고 표기: 실제 발송이 열리면 모든 소식 메일 제목 앞에 `(광고)`, 본문에 발신자 명칭·연락처와 무료 수신거부 방법을 넣는다(`sendMarketingEmail`이 자동으로 붙인다).
- 분기마다 동의자 수, 철회 수, `unknown` 발송 수, 동의 API 오류·충돌 수를 주소·본문 없이 집계해 노션에 남긴다.

## 결과 안내·지속 운영

설정과 수신거부 화면은 Readiary 명칭, 동의/철회 처리 결과와 날짜를 표시한다. 캠페인 운영 전 KISA 최신 가이드에 맞춰 처리 결과 통지와 2년 주기 수신동의 확인 운영을 연결한다. 이 PR은 정기 확인 스케줄러나 알림 메일을 발송하지 않는다. 동의 수집을 활성화할 때 운영 담당자와 정기 확인 일정을 기록한다.

기존 개인정보·탈퇴 운영 절차에 이메일 테이블 삭제 확인을 추가한다. DB 복구 시 완료한 탈퇴/철회를 재반영한다. `unknown` 발송 수와 API 오류·충돌은 주소·본문·토큰 없이 집계한다. 서버 장애 시 확인되지 않은 대상을 임의로 발송하지 않는다.

## 검증

- `node supabase/tests/run-email-consent-contract.mjs`: 메모리 PostgreSQL에서 RLS, 원자적 가입, 재시도·경합, 수신거부, 주소 변경, 장기 재전송 차단, 탈퇴 삭제.
- Vitest: API 인증·출처·계정 변경, 형식/문구 버전, 저장 실패, 토큰 경로, Resend 실패 차단·멱등 키, UI 오류/재시도/충돌.
- 브라우저 검증은 모의 API로 실제 변경 컴포넌트를 렌더링한다. 실제 Supabase 통합, Resend 메일 전달, iOS 설치 PWA와 실기기는 별도 검증 대상이다.

참고: [Resend 수신거부](https://resend.com/docs/dashboard/emails/add-unsubscribe-to-transactional-emails), [멱등 키](https://resend.com/docs/dashboard/emails/idempotency-keys), [KISA 불법스팸대응센터](https://spam.kisa.or.kr/).

2026-10-07 로컬 검증 결과: 전체 Vitest 536개와 SQL 시나리오 27개 통과, TypeScript 및 프로덕션 빌드 통과(합성 Supabase URL·키), ESLint 오류 0개·기존 경고 4개. Chromium 320px/390px 라이트·다크에서 기본 미선택, 거부해도 가입 버튼 활성, 키보드 선택·저장, 설정 철회, 조회 오류 재시도, 저장 오류 후 동일 요청 재시도, 가입 입력 유지, 비로그인 수신거부를 모의 API로 확인했다. 운영 인증·DB·Resend 전송과 실기기 결과는 포함하지 않는다.
