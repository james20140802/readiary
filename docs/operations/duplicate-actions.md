# 저장 요청과 중복 조작 방지

## 사용자 동작

- 기록·책·댓글 생성은 첫 제출의 UUID와 내용을 탭별 sessionStorage에 보관한다.
  연타, 응답 유실, 15초 시간 초과, 화면 재열기 후 재시도는 같은 ID를 보낸다.
- 결과가 불확실하면 입력을 고정하고 `저장 확인·재시도`로 확인한다. 요청 중에는
  시트 닫기·취소·삭제·대상 변경을 막는다. 시간 초과 뒤에는 닫을 수 있지만 보관된
  제출은 유지한다. 확정된 입력 오류에는 수정 기회를 준다.
- 저장 성공 후 화면 이동이 끝나기 전에는 저장 버튼을 다시 풀지 않는다. 이동이
  늦으면 목적지 링크를 사용할 수 있다. 로그인·온보딩·비밀번호·프로필도 같다.
- 계정 전환·로그아웃에서 이전 계정 제출과 표시 내용을 지운다. 비밀번호·인증
  토큰은 이 보관함에 넣지 않는다. 서로 다른 탭에서 독립적으로 시작한 제출은
  서로 다른 의도다. 같은 문장을 나중에 다시 기록하는 것을 금지하지 않는다.
- 기록 수정 응답을 잃으면 현재 행을 읽어 제출 내용과 비교한다. 확인되지 않으면
  재저장을 막고 새로고침으로 확인하게 한다. 댓글 삭제 실패도 현재 목록을 읽는다.
- 친구 수락·거절은 한 요청의 잠금을 공유한다. 완독·완독 취소도 책별 잠금을 공유하며
  이미 완독인 책의 finished_at을 연타로 덮어쓰지 않는다.

## API와 DB 계약

| 경로 | 선택적 요청 필드 | 재시도 결과 |
| --- | --- | --- |
| POST /api/entries/new | client_entry_id | 같은 entries 기본키의 기존 ID 반환 |
| POST /api/comments | client_comment_id | 본인·기록·답글 대상·내용이 같은 기존 댓글 반환 |
| POST /api/books/new | client_request_id | 같은 사용자·ID·제출의 book_id와 user_book_id 반환 |

기록과 댓글은 기존 UUID 기본키로 중복을 제한한다. 댓글 재시도는 알림을 다시
발송하지 않는다. 기존 알림 RPC의 best-effort 전달 보장은 바꾸지 않았다.

책 등록은 `register_book_idempotently` RPC가 사용자/요청별 transaction advisory
lock을 잡고 공용 책 생성·재사용, 개인 책장 연결, 결과 기록을 한 트랜잭션에 담는다.
ISBN이 있으면 기존 공용 책을 재사용하며 다른 사용자가 저장한 서지 정보를 바꾸지
않는다. ISBN이 없으면 해당 요청에서 한 번만 새 책을 생성한다.

`book_registration_requests`는 RLS로 본인 SELECT/INSERT만 허용한다. INSERT는
결과가 본인의 실제 책장 행인지 확인한다. UPDATE/DELETE 권한이 없으며 책장 행을
지워도 결과를 보존해 옛 요청이 책을 재생성하지 않게 한다. 계정 삭제 시에는 함께
삭제된다. 같은 ID에 다른 책 내용은 409다. 함수는 SECURITY INVOKER이며
PUBLIC/anon 실행 권한을 회수한다. 사용자 ID는 본문 대신 auth.uid()에서 결정한다.

구버전 클라이언트의 요청 ID 생략은 허용한다. 책 등록의 경우 서버가 ID를 만들므로
두 단계 쓰기의 원자성은 얻지만, 구버전의 별도 재요청을 중복 제거할 수는 없다.
이후 ID 필수화는 별도 호환성 결정이다. 기존 중복 데이터는 삭제하지 않는다.

## 배포 순서

1. `20260920150543_register_book_idempotently.sql`을 검토하고 별도 승인 후 적용한다.
2. 함수 정의·RLS·권한과 migration history를 읽어 확인한다.
3. 새 RPC를 호출하는 앱을 배포한다. 마이그레이션 전에 새 API를 배포하면 책 등록이
   실패한다. 프로덕션 마이그레이션과 배포는 이 구현 검증에 포함되지 않았다.
4. API 409/500, 등록 후 책장 노출, 세션 만료 이동을 확인한다. 로그에 본문·개인정보·
   키를 남기지 않는다. 롤백은 이전 앱으로 되돌리되 결과 테이블은 보존한다.

## 검증 범위

- 자동 테스트: API 재시도·소유권·다른 내용 충돌·유실된 수정 응답 확인·저장소 정리.
- 실제 PostgreSQL 16 격리 컨테이너: 동일 ID 8개 동시 요청에 한 번 생성, 서로 다른
  ID의 동시 ISBN 재사용, 다른 payload 경쟁, 음수/0 쪽수 거부, 중간 실패 rollback,
  본인/타인/anon 접근, 결과 보존. 대표 스키마 기반이며 전체 운영 스키마 재현은 아니다.
- Chromium 실제 컴포넌트 + 합성 API/auth/router: 연타·Enter 제출, 이동 대기,
  응답 유실·재마운트·같은 ID 재시도, 실제 15초 시간 초과, 계정 전환,
  검색 확인창 재열기, 댓글 입력 유지, 시트 닫기·삭제·Esc 차단, 수락/거절 상호 잠금.
- 프로덕션 빌드는 합성 Supabase URL/key로 수행한다. 실제 인증·Supabase 연결·
  Next 서버의 로그인 후 경로 전환·실제 메일·공유 다이얼로그·iOS 설치형 PWA와
  VoiceOver는 이 합성 컴포넌트 검증으로 확인했다고 간주하지 않는다.

PostgreSQL 검증은 비어 있는 전용 Docker 컨테이너에만 실행한다:

```sh
python3 supabase/tests/run-registration-contract.py <격리된-테스트-컨테이너>
```

이 스크립트는 테스트 스키마를 생성한다. 운영 컨테이너나 기존 데이터가 있는
컨테이너를 대상으로 실행하지 않는다.
