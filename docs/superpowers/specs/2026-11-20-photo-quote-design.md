# 사진에서 문장 옮기기 — 설계

2026-11-20 · 브레인스토밍 결과. 표시가 없는 결정은 사용자가 정했고, *(설계자 판단)* 표시는 대화 중 제안해 사용자가 반대하지 않았거나 설계자가 정한 판단이다.

실험: [docs/design/photo-quote-2026-11/](../../design/photo-quote-2026-11/) — `pick-spike.html`(사진 위에서 문장 고르기, 사용자가 실기기에서 써 보고 조작을 확정함)과 `pick-spike-server.cjs`(Google Vision 호출과 응답 정리). 실험은 조작감과 응답 모양을 보여 주는 조각이며, 색·서체·컴포넌트는 런타임 토큰과 공용 컴포넌트를 따른다. 실험 페이지의 "돋보기" 켜고 끄는 버튼은 비교용이었고 제품에는 넣지 않는다.

옛 시안 [concept-2026-10/home2.html](../../design/concept-2026-10/home2.html)의 "사진으로 옮기기" 카메라 버튼(제안 표시)이 출발점이다.

## 왜

Readiary는 기록하는 행동의 비용을 낮추는 것이 제품의 축이다. 지금은 책의 문장을 남기려면 긴 문장도 손으로 다 옮겨 적어야 한다. 책 페이지를 찍고 남기고 싶은 문장만 손가락으로 골라 문장 칸에 넣을 수 있으면, 긴 문장과 외국어 문장을 남기는 비용이 크게 줄어든다.

## 목표

- 책 페이지를 찍거나 앨범에서 골라, 사진 위에서 원하는 문장만 골라 기록 폼의 문장 칸에 넣는다.
- 한국어 인쇄체를 정확히 읽고, 영어·일본어·한자가 한 페이지에 섞여 있어도 읽는다.
- 고른 글은 기존 기록 폼에서 고쳐 쓴 뒤 남긴다. 별도의 수정 화면을 만들지 않는다.
- 작은 글씨도 고를 수 있도록 사진을 키우고, 고르는 동안 손가락에 가린 자리를 볼 수 있다.
- 데스크톱에서도 쓸 수 있다. 휴대폰으로 찍어 둔 사진을 노트북에서 열어 마우스로 고른다.

## 비목표

- **사진 보관.** 사진은 서버에도 기기에도 남기지 않는다. 기록에 사진을 첨부하는 기능이 아니다.
- **쪽 번호·책 제목 자동 인식.** 사진에서 쪽 번호를 읽어 채우지 않는다.
- **손글씨 인식 보장.** 읽히면 쓰되, 인쇄체만 목표로 한다.
- **세로쓰기와 여러 단으로 짜인 페이지.** 낱말을 잡고 잇는 방식은 가로쓰기 한 단을 전제로 한다. 세로쓰기 책이나 2단 편집은 읽히더라도 고르기가 어긋날 수 있으며, 확인 대상에서 뺀다. *(설계자 판단)*
- **종이책과 전자책 화면의 구분.** 무엇을 찍었는지 가리지 않고, 동의 문구에서도 구분하지 않는다. 이 기능은 전자책의 보호 장치를 우회하지 않으며, 화면을 찍는 것은 이용자가 하는 일이다. 전자책 화면 촬영에 대한 판례는 확인하지 못했다는 점을 위험으로 안고 간다. *(설계자 판단)*
- **한 사진에서 떨어진 여러 부분을 한꺼번에 고르기.** 이어진 한 구간만 고른다. 더 필요하면 다시 연다.
- **기기 안 인식(오프라인).** 실험에서 Tesseract.js는 한국어 정확도와 띄어쓰기 복원이 부족했다(아래 "접근").
- **이용 약관 개정, 문장 길이 상한, 발췌집 공유 제한.** 법적 검토에서 권장 사항으로 나왔으나 이 기능의 범위가 아니다. 약관 제6조 3항이 이미 인용 범위와 회원 책임을 정하고 있다. *(설계자 판단)*

## 반목표 (기술적으로 돼도 실패인 것)

- 동의하지 않은 사람의 사진이 Google로 전송되는 것.
- 사진이나 읽어 낸 글 전체가 서버 로그·DB·Storage·PWA 캐시에 남는 것.
- Vision API 키가 브라우저로 내려가는 것.
- 문장 칸에 쓰던 글이 사진에서 고른 글로 말없이 덮어써지는 것.
- 고르는 화면을 닫았더니 쓰던 기록 폼의 내용(문장·생각·책 선택)이 사라지는 것.
- 한 계정이 제한 없이 호출해 요금이 쌓이는 것.
- 드래그를 할 수 없는 사람(키보드, 화면 읽기 프로그램)이 이 기능으로 아무것도 가져올 수 없는 것.

## 제약

- 네이티브 앱이 아니라 PWA다. iOS Live Text, Android ML Kit 같은 OS 인식 기능은 웹에서 결과를 받을 API가 없어 쓸 수 없다.
- iOS 설치형 PWA에서 `getUserMedia`(실시간 카메라)는 멈춤 버그가 반복 보고됐다. 촬영은 파일 입력으로 OS 카메라를 연다.
- 개인정보 처리방침은 2026-11-13 공고, 2026-12-13 시행 개정판이 걸려 있다. 이 날짜와 `ACCOUNT_DELETION_EFFECTIVE_AT`을 밀지 않는다.
- Vercel 서버리스 함수의 요청 본문 한도(약 4.5MB) 안에서 사진을 보낸다.
- 법적 검토는 2차 자료 기반이며 법률 자문이 아니다. 2026년 개인정보 보호법 개정 조문의 세부는 확인하지 못했다.

## 접근

세 가지를 놓고 실제 화면으로 비교했다.

| | 한국어·혼합 언어 | 드래그로 고른 글 | 걸리는 점 |
|---|---|---|---|
| OS 내장 인식 | 좋음 | — | PWA에서 호출할 수 없음 |
| 기기 안 (Tesseract.js) | 한 글자 틀림, 일본어는 언어 모델을 추가해야 읽음 | 한글을 글자 단위로 쪼개 돌려줘 띄어쓰기가 망가짐 | 언어마다 모델을 내려받음 |
| **Google Cloud Vision** (채택) | 정확 | 띄어쓰기 정보가 있어 자연스럽게 이어짐 | 사진이 국외로 전송됨 |

사용자가 실험 페이지에서 실제 책으로 두 방식을 써 보고 Google Vision을 골랐다. `DOCUMENT_TEXT_DETECTION`은 낱말마다 좌표와 띄어쓰기 종류를 주고, 언어를 자동으로 감지하며, 동기 호출은 사진을 디스크에 저장하지 않고 학습에 쓰지 않는다고 [공식 문서](https://cloud.google.com/vision/docs/data-usage)에 적혀 있다. 월 1,000장 무료, 이후 1,000장당 $1.50이다.

만드는 방식은 앱 서버의 인증된 경로에서 Vision을 호출하는 한 가지다. 브라우저에서 Google을 직접 호출하면 키가 노출되고, Supabase Edge Function으로 빼면 인증·배포 경로만 늘어난다.

### 진입점

기록 폼이 두 계열이라 버튼도 두 곳에 둔다. *(설계자 판단 — 사용자가 "지금 있는 기록 폼에 입력되는 형태"로 정했고, 위치는 설계자가 정함)*

- **오늘 화면 Composer** (`components/today/ComposerView.tsx`): 옛 시안대로 공개 토글이 있는 행의 오른쪽에 카메라 아이콘 버튼을 둔다. 고른 글은 `update({ quote })`로 넣는다. 지금 주 입력이 "생각"이어도 문장 칸이 보이도록 연다.
- **`EntryFormBody`의 문장 칸** (`components/entries/EntryFormBody.tsx`): 문장 칸 라벨 줄에 같은 버튼을 둔다. 이 한 곳으로 새 기록 페이지, 수정 페이지, 책 상세의 수정 시트(`EntryEditSheet`)에 모두 적용된다.

버튼의 접근성 이름은 "사진으로 옮기기"다. 기능이 꺼져 있으면(아래 "켜고 끄기") 버튼을 그리지 않는다.

### 동의

**처음 쓸 때 동의를 받고, 방침 시행을 기다리지 않고 출시한다.** 동의한 사람만 쓸 수 있다.

- 버튼을 처음 누르면 공용 `Sheet`로 동의 내용을 보여 준다. 문구 초안:
  - 제목: "사진 속 글자를 읽으려면"
  - 본문: "찍은 사진은 글자를 읽기 위해 Google(미국)의 서버로 전송됩니다. Readiary는 사진을 저장하지 않으며, Google도 읽은 뒤 사진을 보관하지 않고 학습에 쓰지 않는다고 밝히고 있습니다. 사진에 함께 찍힌 손이나 메모도 전송되니, 책 페이지만 담아 주세요. 동의하지 않아도 문장을 직접 적어 기록할 수 있습니다."
  - 버튼: "동의하고 계속", "취소"
- 동의는 계정 단위로 서버에 남긴다(시각, 문구 판 번호). 한 번 동의하면 다른 기기에서도 다시 묻지 않는다. 문구 판이 바뀌면 다시 묻는다. *(설계자 판단)*
- 설정 화면에 "사진 글자 읽기 동의"를 두어 철회할 수 있게 한다. 철회하면 다음에 버튼을 누를 때 다시 묻는다. *(설계자 판단)*
- 기존 사용자에게는 운영자가 따로 직접 알린다. 그와 별개로 앱 안의 동의는 모든 사람에게 처음 한 번 보여 준다. 기록으로 남는 동의는 앱 안의 것뿐이기 때문이다. *(설계자 판단 — "나머지 사용자에게는 내가 직접 동의를 받겠다"는 말을 이렇게 읽었다)*

### 사진 받기

- 버튼을 누르면 "사진 찍기"와 "앨범에서 고르기" 두 선택지를 보여 주고, 각각 `<input type="file" accept="image/*" capture="environment">`와 `capture` 없는 입력을 연다. *(설계자 판단)*
- 정밀한 포인터가 있는 기기(데스크톱)에서는 선택지 없이 바로 파일 고르기를 연다. 고르는 화면에 사진 파일을 끌어다 놓아도 받는다. *(설계자 판단)*
- **HEIC도 연다.** 아이폰에서 넘긴 사진은 HEIC일 수 있고, Safari는 바로 열지만 Chrome·Firefox는 열지 못한다. 먼저 브라우저로 열어 보고, 실패한 파일이 HEIC/HEIF일 때만 변환 모듈을 그때 내려받아 기기 안에서 JPEG로 바꾼다. 변환 모듈은 첫 화면 묶음에 넣지 않고, 사진을 서버로 보내 변환하지 않는다. 변환 중에는 "사진을 준비하는 중…"을 보여 준다.
- 변환까지 실패하거나 그 밖의 열 수 없는 형식이면 "이 사진을 열지 못했어요. 다른 사진으로 다시 골라 주세요."로 알린다. *(설계자 판단)*
- 받은 사진은 기기에서 캔버스에 다시 그려 회전을 바로잡고, 긴 변 2,000px로 줄이고, JPEG(품질 0.9)로 만든다. 이 과정에서 EXIF(위치 등)가 떨어진다. 실험과 같은 값이다.
- 사진은 고르는 화면이 열려 있는 동안 메모리에만 있다. 닫으면 `URL.revokeObjectURL`로 놓는다. sessionStorage 초안에는 글만 들어간다.

### 고르는 화면

전체 화면 대화상자다. 수정 시트 위에서도 열리므로 `Sheet`(z-100)보다 위에 쌓인다. 조작은 실험 페이지에서 사용자가 확정한 그대로다.

| 조작 | 결과 |
|---|---|
| 두 손가락 벌리기 | 최대 6배까지 키운다 |
| 짧게 두 번 두드리기 | 그 자리를 2.5배로 키우고, 다시 두드리면 돌아온다 |
| 한 손가락으로 끌기 | 사진을 옮긴다 |
| 낱말을 0.32초 누른 채 끌기 | 누른 낱말부터 손가락이 있는 낱말까지 글 선택처럼 이어서 고른다 |
| 양 끝 손잡이 끌기 | 고른 구간을 늘리거나 줄인다 |
| 고르는 중 가장자리에 닿기 | 사진이 그쪽으로 조금씩 밀린다 |
| 고르는 중 (항상) | 손가락 위에 돋보기가 떠서 가린 자리를 지금 크기의 1.6배로 보여 준다. 위에 자리가 없으면 손가락 아래에 뜬다 |

위 표는 손가락(터치) 기준이다. 누른 뒤 10px 넘게 움직이면 고르기가 아니라 옮기기로 본다.

**마우스와 트랙패드** *(사용자가 데스크톱 지원과 "확대·축소 버튼은 데스크톱에서만"을 정했고, 세부 조작은 설계자 판단)*

| 조작 | 결과 |
|---|---|
| 낱말 위에서 누른 채 끌기 | 길게 누르지 않고 바로 고른다(글 선택과 같다) |
| 휠, 트랙패드 두 손가락 쓸기 | 사진을 옮긴다 |
| Ctrl/⌘ + 휠, 트랙패드 벌리기 | 키우고 줄인다 |
| 확대(+)·축소(−)·맞춤 버튼 | 사진 틀 구석에 둔다. 마우스처럼 정밀한 포인터가 있는 기기에서만 보인다 |
| 더블클릭 | 그 자리를 2.5배로 키우고, 다시 하면 돌아온다 |
| 양 끝 손잡이 끌기 | 고른 구간을 늘리거나 줄인다 |

- 손가락인지 마우스인지는 화면 폭이 아니라 그 조작의 포인터 종류(`pointerType`)로 가른다. 터치가 되는 노트북에서 손가락으로 만지면 손가락 규칙을 따른다.
- 돋보기는 손가락으로 고를 때만 뜬다. 마우스는 가리는 것이 없다.
- 키보드: `+`/`-`로 키우고 줄이고, 화살표로 옮긴다. 고르기는 "전부 가져오기"로 대신한다.
- 넓은 화면(lg 이상)에서는 전체 화면 대신 화면을 거의 채우는 가운데 창으로 연다. 사진은 창 높이에 맞춰 보여 준다.
- 인식된 낱말의 상자는 그리지 않는다. 고른 구간만 accent 색으로 칠한다.
- 낱말을 찾을 때는 손가락 아래 낱말이 없으면 가장 가까운 낱말을 잡되, 위아래 줄보다 같은 줄을 먼저 잡는다(실험의 `wordAt`).
- iOS에서 사진 선택·길게 누르기 메뉴가 뜨지 않도록 화면 안의 기본 터치 동작을 막는다(실험에서 실제로 겪은 문제다).
- 고른 글은 낱말을 Vision의 띄어쓰기 정보로 잇는다. 줄이 바뀌는 곳은 띄어쓰기 한 칸으로 잇는다. **줄 끝에서 낱말이 잘려 다음 줄로 넘어간 경우 Vision은 따로 알려 주지 않으므로 불필요한 띄어쓰기가 생길 수 있다. 사용자가 폼에서 고친다.** 알려진 한계다.
- **"이 문장 쓰기"**: 고른 구간이 있을 때만 켜진다. 누르면 화면을 닫고 고른 글을 문장 칸에 넣는다.
- **"전부 가져오기"**: 읽은 글 전체를 문장 칸에 넣는다. 드래그를 할 수 없는 사람이 키보드만으로 쓸 수 있는 길이며, 폼에서 필요 없는 부분을 지운다. *(설계자 판단)*
- **"다시 찍기"**: 사진 받기로 돌아간다. **닫기**와 Esc는 아무것도 넣지 않고 닫는다.
- 움직임 줄이기 설정에서는 확대 전환을 즉시 바꾼다.

상태별 화면:

| 상태 | 보이는 것 |
|---|---|
| 읽는 중 | 사진을 먼저 보여 주고 "글자를 읽는 중…". 이 동안에도 키우고 옮길 수 있다 |
| 읽음 | 안내 한 줄 "첫 낱말을 길게 누른 채 끝까지 끌어 보세요" |
| 글자 없음 | "이 사진에서 글자를 찾지 못했어요. 더 밝은 곳에서 다시 찍어 보세요." + 다시 찍기 |
| 실패(네트워크·서버) | "글자를 읽지 못했어요." + 다시 시도(같은 사진) + 다시 찍기 |
| 하루 한도 | "오늘은 사진을 더 읽을 수 없어요. 내일 다시 쓸 수 있어요." + 닫기 |
| 세션 만료 | 기존 `apiFetch`의 처리(갱신 1회 재시도 → 로그인)를 따른다 |

### 문장 칸에 넣기

- 문장 칸이 비어 있으면 그대로 넣는다.
- 이미 글이 있으면 덮어쓰지 않고, 빈 줄 하나를 두고 뒤에 이어 붙인다. *(설계자 판단)*
- 넣은 뒤 문장 칸에 포커스를 두고 커서를 끝에 놓는다.

## 서버

### 글자 읽기 경로

`POST /api/photo-text` *(이름은 설계자 판단)*

- 요청 본문은 JPEG 바이트 그대로(`Content-Type: image/jpeg`). 2MB를 넘으면 413으로 거절한다. 줄인 사진은 보통 수백 KB다.
- 순서: 로그인 확인 → 기능 켜짐 확인 → 동의 확인과 하루 사용 횟수 올리기(한 번의 DB 호출) → Vision 호출 → 응답 정리.
- Vision은 REST `images:annotate`에 `DOCUMENT_TEXT_DETECTION` 하나로 호출한다. 키는 `X-Goog-Api-Key` 헤더로 보낸다. 15초 안에 답이 없으면 실패로 본다.
- 응답:
  ```json
  { "width": 1500, "height": 2000,
    "words": [{ "text": "책을", "box": [412, 388, 470, 421], "sep": " " }] }
  ```
  `box`는 사진 픽셀의 `[x0, y0, x1, y1]`, `sep`는 이 낱말 뒤에 붙일 글자다. Vision의 `detectedBreak`가 `HYPHEN`이면 빈 문자열, 그 밖의 값이 있으면 띄어쓰기 한 칸, 없으면 빈 문자열이다(실험 서버와 같다). 낱말 순서는 Vision이 준 순서를 그대로 쓴다.
- 오류는 `code`로 구분한다: `session_expired`(401, 기존 계약), `consent_required`(403), `daily_limit`(429), `too_large`(413), `read_failed`(502), `disabled`(404).
- 사진과 읽은 글은 로그에 남기지 않는다. 남기는 것은 사용자 id, 시각, 결과 종류뿐이다.
- Vision 호출이 실패한 경우에도 하루 횟수는 되돌리지 않는다. *(설계자 판단 — 실패를 반복시켜 호출을 쌓는 것을 막는다)*

### 동의와 하루 한도

- 동의는 계정당 한 줄(동의 시각, 문구 판, 철회 시각)로 남긴다. 본인만 읽을 수 있고, 쓰기는 서버 경로나 RPC로만 한다. 이메일 소식 동의(`20261007090000_email_marketing_consent.sql`)의 "본인 읽기, 직접 쓰기 금지" 방식을 따르되 사건 이력 테이블까지는 두지 않는다. *(설계자 판단)*
- 하루 한도는 한 계정에 **30장**이다. 한국 시간 자정에 초기화한다. 횟수만 세고 사진이나 글은 저장하지 않는다. *(설계자 판단)*
- 동의 확인과 횟수 올리기는 하나의 RPC에서 원자적으로 처리해, 동시에 여러 요청을 보내도 한도를 넘지 못하게 한다.
- 계정을 지우면 두 기록 모두 함께 지워진다(`on delete cascade`).
- 동의 남기기·철회는 `POST /api/photo-text/consent`, `DELETE /api/photo-text/consent`로 한다. 현재 동의 여부는 버튼을 누를 때 확인한다. 닫힌 기능을 위해 페이지를 열 때마다 미리 가져오지 않는다.

### 켜고 끄기

- `NEXT_PUBLIC_PHOTO_QUOTE_ENABLED === 'true'`일 때만 버튼을 그린다(Google 로그인의 env 플래그 선례). 서버는 이 값과 `GOOGLE_VISION_API_KEY`가 모두 있을 때만 동작하고, 아니면 `disabled`를 돌려준다.
- 키는 Vercel 환경 변수로만 두며 Cloud Vision API로 제한한 키를 쓴다. 발급과 등록은 운영자가 한다.
- 운영자는 실험 때 이미 키를 만들어 두었다. 만드는 동안의 미리보기 서버 확인에는 운영자가 승인된 환경 파일에 키를 넣어 주며, 자동 시험은 Vision을 흉내 내므로 키가 필요 없다. 키를 worktree에 복사하거나 로그·PR에 적지 않는다.

## 언어의 범위

- Vision은 언어를 자동으로 감지하며 한 페이지에 여러 언어가 섞여 있어도 함께 읽는다. 언어를 고르는 설정은 두지 않는다.
- 실험에서 확인한 것은 한국어, 영어, 일본어(가로쓰기)와 이 셋이 섞인 페이지다. 그 밖의 언어는 Vision이 지원하더라도 이 기능으로 확인하지 않았다.
- 영어의 줄 끝 하이픈: Vision이 하이픈 줄바꿈으로 알려 준 곳은 하이픈 없이 붙인다. 줄 끝에 걸린 원래 하이픈 낱말(예: well-known)도 붙어 버릴 수 있다. 사용자가 폼에서 고친다.
- 아랍어·히브리어처럼 오른쪽에서 왼쪽으로 쓰는 글은 읽히더라도 끌어 고르는 방향과 잇는 순서가 맞지 않을 수 있다. 지원 대상이 아니다.
- 띄어쓰기가 없는 언어(일본어·중국어)는 Vision이 나눈 낱말 단위로 고른다. 한 글자 단위로 다듬을 수는 없고, 폼에서 고친다.

## 법적 검토 요약

- 자기 책을 찍어 문장을 개인 기록으로 남기는 것은 저작권법 제30조(사적이용 복제)의 전형적인 경우이며, 손으로 옮겨 적는 것과 성격이 같다. 위험은 낮다.
- 친구 공개·외부 링크·발췌집은 이미 있는 기능이고, 이 기능이 새 공개 경로를 만들지 않는다. 다만 긴 문장을 옮기기 쉬워져 양이 늘 수 있다. 약관 제6조 3항이 인용 범위와 회원 책임을 정하고 있고, 문의 창구(`SUPPORT_EMAIL`)가 있다.
- 서버가 사진을 잠깐 다루는 것은 저장 없이 처리 뒤 버리는 구조라 제35조의2(일시적 복제)의 취지에 맞는다.
- 사진을 저장하지 않아도 전송은 개인정보 처리다. 처리방침의 위탁·국외 이전 고지가 필요하고, 이 설계는 방침 개정과 사전 동의로 대응한다.
- 확인하지 못한 것: 2026년 개인정보 보호법 개정 조문의 세부, 전자책 화면 촬영과 제104조의2의 관계에 대한 판례.

## 확인

- **HEIC**: 실제 아이폰 HEIC 사진을 데스크톱 Chrome과 Safari에서 열어 본다.
- **단위 시험**: 낱말 잇기(띄어쓰기·줄바꿈·하이픈), 구간 고르기와 손잡이로 뒤집힌 구간 정리, 가까운 낱말 찾기, 문장 칸 이어 붙이기, 사진 줄이기 계산.
- **경로 시험**: Vision을 흉내 내어 로그인 없음·동의 없음·한도 초과·큰 본문·Vision 실패·글자 없음·정상 응답을 확인한다. 사진과 글이 로그에 찍히지 않는지 본다.
- **DB**: 동의 없는 계정과 다른 계정의 동의·횟수를 읽거나 쓸 수 없는지, 동시 요청으로 한도를 넘지 못하는지를 DB 계약 검사에 더한다.
- **화면**: 모바일 폭과 데스크톱 폭, 라이트·다크, 키보드(버튼 → 동의 → 전부 가져오기 → 폼), 마우스(끌어 고르기, 휠, 확대·축소 버튼), 읽는 중·글자 없음·실패·한도 상태.
- **실기기**: 길게 눌러 고르기, 두 손가락 확대, 돋보기, 사진 선택 메뉴가 뜨지 않는지는 iOS Safari, iOS 설치형 PWA, Android Chrome에서 사람이 확인한다. WebKit 에뮬레이션 결과를 실기기 확인으로 적지 않는다.
- **공개 범위**: 동의 철회 뒤 호출이 거절되는지, 사진이 Storage·PWA 캐시에 없는지 확인한다.

## 만드는 사람에게 맡기는 것

- 컴포넌트와 파일 나누기, 고르는 화면의 구현 방식(실험의 포인터 처리와 변환 계산을 옮기되 React에 맞게 다듬는다).
- 동의·횟수 테이블과 RPC의 이름과 모양.
- 카메라 버튼의 정확한 자리와 여백, 고르는 화면의 세부 배치(토큰과 공용 컴포넌트를 따른다. 고르는 화면의 바탕은 사진이 잘 보이도록 정한다).
- 사진 받기의 두 선택지를 어떤 형태(작은 메뉴, 시트)로 보여 줄지.
- 방침 개정의 날짜 상수 구성(Web Push 선례를 따른다).
- 오류 문구의 다듬기.
- HEIC 변환 라이브러리의 선택(libheif 계열, 예: `heic-to`, `heic2any`). 필요할 때만 내려받는지, 라이선스가 `NOTICE`에 맞는지, Chrome에서 실제 아이폰 HEIC 사진이 열리는지를 확인한다.

## 운영자가 할 일

- Vercel에 `GOOGLE_VISION_API_KEY`와 `NEXT_PUBLIC_PHOTO_QUOTE_ENABLED`를 등록한다. 실험에 쓴 키는 지우고 새로 만드는 것을 권한다.
- Google Cloud에 예산 알림을 건다.
- 마이그레이션을 프로덕션에 적용한다.
- 기존 사용자에게 새 기능과 사진 전송을 직접 알린다.
- 실기기에서 조작을 확인한다.

## 만들면서 정한 것 (2026-11-20)

계획은 [구현 계획](../plans/2026-11-20-photo-quote.md)이다. 아래는 위 설계와 다르거나 설계가 맡긴 것을 구현하며 정한 것이다.

- **HEIC 변환은 `heic-to`**(LGPL-3.0, libheif)를 쓴다. `heic2any`는 MIT지만 2023년 이후 갱신이 없다. 고치지 않은 그대로 별도 스크립트 파일로 나뉘어 필요할 때만 내려받아지며 `NOTICE`에 적었다.
- **정밀 포인터 기기의 첫 번째 사용**에는 "사진 고르기" 버튼 하나가 있는 시트를 거친다. 서버에 동의 여부를 물은 뒤에는 브라우저가 파일 고르기를 막을 수 있어서다. 같은 탭에서 동의를 한 번 확인한 뒤로는 설계대로 바로 파일 고르기를 연다.
- **고르는 화면의 바탕**은 사진 자리만 어둡게(`scrim`) 하고 위아래 줄은 `sheet` 토큰이다. 고른 글은 아래 줄에 미리 보여 준다.
- 정밀 포인터에서는 "다시 찍기"를 "다른 사진 고르기"로 적는다.
- 마우스로 낱말을 한 번 누르면 그 낱말 하나가 골라지고, 두 번 누르면 확대된다.
- 확대 전환에는 애니메이션을 두지 않는다(실험과 같다).
- DB: `photo_text_consents`, `photo_text_usage`, RPC `begin_photo_text_read`·`set_photo_text_consent`·`withdraw_photo_text_consent`·`photo_text_consented`. 탈퇴를 신청한 계정은 읽기와 새 동의를 할 수 없고 철회만 할 수 있다.
- 방침의 이 항목 공고일은 2026-11-21, 시행일은 2026-11-28로 적었다. 실제 배포일에 맞춰 고친다.
