# 계정 탈퇴와 14일 복구 유예 설계

작성일: 2026-11-12 · 상태: 사용자 결정 반영, 최종 확인 대기

## 왜 만드나

지금은 탈퇴하려면 운영자에게 메일을 보내야 한다(약관 제8조, 방침 제8조 3항). 독자가 설정 화면에서 직접 탈퇴할 수 있게 한다.

탈퇴는 되돌리기 어려운 결정이라, 마음을 바꾼 독자가 기록을 잃지 않도록 **14일 동안 복구할 수 있게** 한다. 이 기간에 정보를 남기는 이유는 **복구 하나뿐**이다.

### 법적 보관 의무에 대한 판단

2026-11-11 대화에서 확인한 내용이다. 법률 자문을 받은 결과는 아니다.

- Readiary에는 결제가 없고 비상업적으로 운영된다. 따라서 전자상거래법의 거래 기록 보관(5년·3년) 대상이 아니다.
- 접속 로그(통신비밀보호법 3개월)를 보관해야 한다면, 그것은 Vercel·Supabase 로그 설정의 문제다. 탈퇴자 정보를 앱 DB에 남길 근거가 되지 않는다. 조문 원문은 확인하지 못했다.
- 개인정보 보호법 제21조에 따라, 보존 의무가 없는 정보는 목적을 달성하면 지체 없이 파기한다.
- 결론: 법 때문에 남기는 항목은 없다. 14일 유예는 서비스가 선택한 정책이므로 방침에 항목·목적·기간을 적고 미리 공지한다.

## 목표

1. 설정 화면에서 본인 확인을 거쳐 탈퇴를 신청한다.
2. 신청하는 즉시 다른 사람에게서 그 독자의 흔적이 사라진다. 모든 기기에서 로그아웃되고 알림과 메일 발송이 멈춘다.
3. 14일 안에 다시 로그인하면 탈퇴를 취소하고 신청 전 상태 그대로 돌아온다.
4. 14일이 지나면 프로필 사진 파일까지 모두 지우고 Auth 사용자를 삭제한다.
5. 약관과 방침을 개정·공지하고, 시행일부터 기능을 연다.

## 하지 않는 것

- 복구용 사본, 백업 테이블, 익명화 보관. 유예 중에도 데이터는 원래 자리에 그대로 두고 **숨기기만** 한다.
- 재가입 악용 방지용 이메일 해시 보관이나 재가입 제한 기간.
- 탈퇴 사유 설문(필수). 받더라도 선택 입력이어야 하고, 이번 범위에서는 받지 않는다.
- 운영자 수동 탈퇴 절차 폐지. 메일 요청 경로는 앱에 접근할 수 없는 사람을 위해 남긴다. 다만 메일 요청도 운영자가 같은 신청 상태를 기록해 **똑같이 14일 유예·숨김·자동 삭제를 거친다.** 방침이 약속하는 규칙을 하나로 유지하기 위해서다. 운영자용 신청 방법(서비스 롤 RPC 또는 SQL)을 운영 문서에 적는다. *(설계자 판단)*

## 실패로 보는 것 (anti-goals)

- 유예 중인 독자의 문장·프로필·댓글이 친구 피드, 검색, 외부 공유 링크, 알림에 남아 보인다.
- 14일 뒤 Auth 사용자는 지워졌는데 Storage 파일이나 연결 행이 남는다. 또는 파일 삭제에 실패했는데 완료로 처리된다.
- 복구했는데 친구 관계, 기록, 발췌집, 반응 중 일부가 사라져 있다. 단, 푸시 구독은 예외다(아래 참고).
- 실수로 한 번 눌러서 탈퇴된다.

## 사용자 흐름

### 1. 신청 (설정 → 계정)

- 설정의 `AccountSection` 맨 아래에 보조 행동으로 "탈퇴하기"를 둔다. 파란 강조색이나 먹 배경의 주요 버튼으로 만들지 않는다.
- 누르면 `Sheet`가 열린다. 시트 안에서 다음 순서로 안내한다.
  1. 무엇이 일어나는지 독자의 언어로 설명한다. 친구에게 바로 보이지 않게 되고, 14일 안에 로그인하면 되돌릴 수 있으며, 그 뒤에는 기록이 모두 지워진다.
  2. 완전 삭제 예정일을 날짜로 보여 준다(KST). 예: "11월 26일에 모두 지워집니다".
  3. 기록 내보내기(기존 `/api/export`) 링크를 둔다.
  4. 본인 확인을 받는다. 서버가 판정하며, 클라이언트의 주장만으로 통과시키지 않는다.
     - 비밀번호 사용자: 현재 비밀번호를 입력받아 서버에서 확인한다. 비밀번호 변경의 "현재 비밀번호 확인" 방식(PR #90)을 재사용한다.
     - 비밀번호가 없는 OAuth 사용자: 지금 세션의 로그인 시각(JWT의 `amr` 타임스탬프 등 서버가 검증할 수 있는 값)이 **10분 이내**여야 한다. 아니면 시트에 "다시 로그인하고 계속"을 보여 준다. OAuth를 왕복한 뒤에는 설정 화면으로 돌아와 탈퇴 시트를 다시 연다. 기존 `PasswordChange.tsx`의 OAuth 분기에는 재인증이 없으므로 새로 만든다. *(설계자 판단)*
  5. 최종 버튼 문구는 "탈퇴 신청"이다.
- 성공하면 모든 세션을 해지(global sign-out)하고, 로그인 화면이나 랜딩으로 보낸다. 그곳에 "탈퇴를 신청했습니다. ○월 ○일까지 로그인하면 되돌릴 수 있어요"라고 안내한다.

### 2. 유예 중 (신청 후 14일)

- 다른 사람에게서 숨길 것:
  - 프로필, 책장, 기록, 발췌집, 독서 통계
  - 다른 사람 글에 남긴 좋아요·댓글(기록과 월간 발췌집 모두)
  - 친구 목록과 친구 검색, 소셜 피드, 외부 공유 링크(`get_public_entry` 등 `shared_at` 경로)
  - 그 독자가 원인인 새 알림. 이미 쌓인 알림은 받은 사람의 알림함에서 그 독자의 행동을 보이지 않게 한다.
- 본인에게 멈출 것: 푸시 발송, 이메일 소식 발송, 이메일 소식 동의 상태는 그대로 두되 발송 대상에서 뺀다.
- 푸시 구독은 신청 시 삭제한다. 기기 주소는 복구할 가치가 낮고 남겨 둘 이유가 없다. 복구한 독자는 기기 알림을 다시 켜야 하며, 복구 화면에서 이를 알린다. *(설계자 판단)*
- 친구 요청: 유예 중인 독자에게 새 친구 요청을 보낼 수 없다. 이미 받은 요청은 그대로 두고 숨긴다.

### 3. 복구

- 유예 중인 계정으로 로그인하면, 앱의 다른 화면 대신 복구 화면(`/account/restore`, 이름은 구현자 판단)으로 보낸다. `proxy.ts`의 온보딩 리다이렉트와 같은 방식으로 처리한다.
- 복구 화면에는 두 가지 행동만 둔다. "탈퇴 취소하고 돌아가기"와 "로그아웃"이다. 삭제 예정일을 함께 보여 준다.
- 취소하면 숨김이 즉시 풀리고 모든 것이 신청 전 상태로 돌아온다.
- 유예 중 같은 이메일로 새로 가입하는 것은 막는다. Auth 사용자가 남아 있으므로 기본적으로 막힌다. 가입 화면의 오류 문구는 "로그인하면 되돌릴 수 있다"고 안내한다.

### 4. 완전 삭제

- 삭제 예정 시각이 지난 계정을 정기 작업이 처리한다.
- 순서는 `docs/operations/privacy-release.md`의 "탈퇴 및 미사용 이미지 처리"를 따른다.
  1. `profiles` 버킷의 해당 UUID 폴더를 페이지 단위로 끝까지 조회해 Storage API로 지운다. 옛 업로드도 포함하며, 메타데이터 행을 SQL로 직접 지우지 않는다.
  2. 파일 삭제가 끝난 것을 확인한 뒤 Auth 사용자를 삭제한다. FK CASCADE로 연결 행이 지워진다.
  3. 실패한 계정은 완료로 처리하지 않고 다음 실행에서 다시 시도한다.
- 공유 서지 정보(`books`)는 방침대로 남을 수 있다.
- **삭제 완료 기록**: 완전 삭제를 마치면 사용자 UUID와 삭제 완료 시각만 담은 기록 한 줄을 남긴다. 이메일, 닉네임, 기록 내용은 넣지 않는다. 이 기록으로는 아무것도 복구할 수 없다. 백업으로 DB를 되돌렸을 때 "이 계정들은 이미 지웠다"는 것을 알고 다시 지우기 위한 목록이다. 기록은 삭제 완료 후 30일이 지나면 정기 작업이 지운다. Supabase 백업과 PITR 보관 기간을 덮는 값이며, 운영 계정의 실제 백업 보관 기간이 30일보다 길다면 그 값에 맞춘다. 이 기록은 서비스 롤만 읽고 쓸 수 있다. *(사용자 결정, 2026-11-12)*
- 시간 순서: 신청(0일) → 유예와 복구 가능(0~14일) → 완전 삭제(14일) → 삭제 완료 기록 보관(14~44일) → 기록 삭제.

## 기술 제약과 방향

- **DB 단일 진실**: 숨김은 UI가 아니라 RLS와 RPC에서 보장한다. PR #84 이후 저장소의 마이그레이션이 RLS의 단일 진실이다. 친구 열람은 대부분 `public.is_friend_with`를 거치지만, `friends`를 직접 조회하는 정책·함수(약 12곳)와 security definer RPC(소셜 피드, 친구 발췌집, 공개 기록 등)가 따로 있다. 모든 경로를 빠짐없이 덮어야 한다.
- **상태 저장 위치**: 권장안은 `profiles.deletion_requested_at timestamptz` 열 하나와 파생 시각(신청 + 14일)이다. 별도 테이블이 더 낫다면 구현자가 정한다. 신청·취소는 본인만, 서버 경로로만 바꿀 수 있어야 한다. 클라이언트가 이 열을 직접 고쳐서 숨김을 풀거나 삭제 시각을 미룰 수 없어야 한다.
- **이미 발급된 토큰**: global sign-out만으로 이미 발급한 액세스 토큰이 즉시 무효화되지 않는다(운영 문서 기존 원칙). 유예 중인 사용자의 쓰기는 RLS 또는 RPC에서도 거부해야 한다. 복구 RPC는 예외다.
- **정기 작업**: 푸시와 같은 방식을 쓴다. Supabase pg_cron과 pg_net이 `CRON_SECRET`으로 보호된 `/api/cron/<이름>`을 호출하고, 라우트는 서비스 롤로 처리한다. 호출은 매일 1회면 충분하다. Vercel Cron은 쓰지 않는다. 설치 SQL은 `supabase/operations/`에 둔다.
- **계약 테스트**: `supabase/tests/`의 기존 계약 테스트 방식으로 검증한다. 유예 중 사용자의 데이터가 친구, 비친구, anon 모두에게 보이지 않는지, 복구 뒤 다시 보이는지, 유예 중 쓰기가 거부되는지 확인한다. CI 필수 검사(Verify DB contracts)에 포함한다.
- **기능 공개 시점**: 약관과 방침 개정의 시행일 전에는 탈퇴 버튼을 보여 주지 않는다. 기존 `feature_rollouts` 또는 날짜 상수(`lib/legal/texts.ts` 패턴)로 막는다.
- **디자인**: 시트, 버튼, 입력은 공용 컴포넌트와 토큰을 쓴다. 위험 행동의 글자색은 기존 `danger` 토큰을 쓴다. 모바일 폭, 라이트·다크, 키보드로 검증한다.

## 약관·방침 개정

- 약관 제8조 1항의 "서비스 안에 탈퇴 기능이 마련되기 전까지는 메일로 요청" 문구를 바꾼다. 설정에서 직접 신청할 수 있고, 메일 요청도 가능하다고 적는다.
- 방침 제3조 1항의 "탈퇴하면 지체 없이 지웁니다"를 바꾼다. 탈퇴를 신청하면 즉시 다른 이용자에게 보이지 않고, 신청 후 14일 동안 복구를 위해 보관한 뒤 지운다. 기간 안에 다시 로그인하면 취소할 수 있다고 적는다.
- 방침의 푸시와 이메일 조항(제3조 4·5항)에서 "탈퇴 시 삭제"의 시점이 유예 종료임을 분명히 한다. 푸시 구독은 신청 시 바로 지운다.
- 기존 개정 절차를 따른다. 현행본은 `lib/legal/archive.ts`에 보관하고, 공고일과 시행일 상수를 갱신하며, 오늘 화면에 안내를 띄운다.
- 공지 기간은 **30일**이다. "바로 지운다"가 "14일 보관 후 지운다"로 바뀌어 보관이 늘어나는 것으로 읽힐 수 있으므로, 불리한 변경 기준을 적용한다. 코드는 먼저 머지하고, 시행일에 탈퇴 버튼을 연다. *(사용자 결정, 2026-11-12)*
- 방침에는 삭제 완료 기록의 항목(사용자 ID, 삭제 시각), 목적(백업 복구 시 삭제 재반영), 기간(삭제 후 30일)도 적는다.
- `docs/operations/privacy-release.md`의 탈퇴 절차를 앱 흐름과 수동 요청 흐름으로 나누어 갱신한다.

## 구현자에게 맡기는 것

- 상태 열과 테이블 구조, RPC 이름, 라우트 경로
- 숨김을 정책에 넣을지 헬퍼 함수로 모을지
- 정기 작업의 배치 크기와 재시도 방식
- 시트와 복구 화면의 세부 문구. 단, 행동과 결과를 말하는 문구 원칙을 지킨다.

## 남은 질문

없음. 2026-11-12에 백업 재반영(삭제 완료 기록 30일)과 공지 기간(30일)을 사용자가 정했다.
